## Files (Kyty branch `hybrid`)

- `src/hybrid/kytyGpuApi.h`: versioned C interface (ABI 1.0) shared by MinGW and clang-cl: init/start/shutdown, memory register/unregister/invalidate, DCB/ACB submit, NID table queries, host callbacks (log, GPU event registration and delivery, memory queries, app0 path). Struct layouts checked with static asserts on both sides.
- `src/hybrid/kytyGpuBridge.cpp`: one naked thunk per NID (`movl $index, %r11d; jmpq *slot(%rip)`, verified with llvm-objdump), so System V arguments and the stack pass through untouched; slots start at a trap that names the NID and aborts; `init` binds them through Kyty's own `LIB_FUNC` tables (`Libs::InitAgcDriver_1`, `Libs::LibGen5::InitVideoOut_1`) and the bridge functions.
- `src/hybrid/kytyGpuNids.inc`, `src/hybrid/kyty_gpu.def`: generated by `tools/hybrid/gen_kyty_gpu_exports.py` from the registry and Kyty's sources; it fails if the game imports a NID Kyty does not implement.
- `tools/hybrid/build_kyty_gpu.py`, `tests/hybrid/kytyGpuLoadTest.c`.

## ABI findings (NID match is not enough)

- Both engines export guest-callable functions with the System V convention (`APS5_VABI`, `KYTY_SYSV_ABI`).
- `Packet` (`addr`, `dw_num` at 8, `flags` at 12, 16 bytes) is identical; `SubmitDcb`, `AgrSubmitDcb`, `SubmitAcb(queue, Packet*)` match.
- `sceAgcDriverRegisterOwner/RegisterResource`: Kyty declares them without arguments, AnyPS5 with handle pointers, but both return `0x8A6C9018` and write nothing, so binding Kyty's is equivalent.
- `sceAgcDriverAddEqEvent`, `sceVideoOutAddFlipEvent`: both take an `int64_t` queue handle, but each engine's handle indexes its own kernel table. The game's queues come from AnyPS5's libkernel, so these go to the bridge, which forwards them to the host (`add_gpu_event`), verified through the thunk with exact arguments.
- `sceAgcCbNopGetSize(16)` returns 64 bytes in both engines (checked through the export).
- The other 75 NIDs are Kyty's HLE implementations of the game ABI (command builders, shader registration, VideoOut with Kyty-owned handles); their layouts were not compared one by one.

## Remaining integration issues (milestone 2)

1. **Renderer start-up in AstroBot.exe:** `start_graphics` returns `KYTY_GPU_E_NOT_IMPLEMENTED`. Kyty's `Init` needs the Config, Log, Timer, Pthread, Profiler, Memory and Graphics lifecycles, insists on its main thread, and `Graphics::WindowRun()` blocks on it; inside AstroBot.exe it needs its own window thread.
2. **Memory adapter (largest):** Kyty's renderer reads guest memory through `Memory::TryReadBacking`, `TryReadGpuCleanBacking`, `IsGpuMapped`, `GuestBackingAlias` and about 20 more, which expect Kyty's own direct-memory backing aliases and page-protection write tracking. AnyPS5's libkernel maps the guest memory. Either AnyPS5 provides a backing alias per direct-memory mapping and notifies the DLL (`register_memory`, currently `KYTY_GPU_E_NOT_IMPLEMENTED`), or the game's direct-memory calls move to Kyty's kernel memory inside the DLL. AnyPS5's own write tracking (write alarms, GetWriteWatch) must not run on the same ranges as Kyty's.
3. **Events GPU → game:** Kyty raises EOP and flip events on its own queues. The bridge must give Kyty a proxy queue per host registration and forward triggers to `deliver_event` (host side: `AgcDriverDeliverEopInterrupt`, equeue trigger).
4. **Loader switch:** AnyPS5's loader binds the 82 imports from the three prx files. Under an engine setting (off by default) it must bind them from kyty_gpu.dll instead, and AnyPS5's libSceAgcDriver/VideoOut must not start their own Vulkan device then (one renderer only).
5. **Runtime DLLs:** kyty_gpu.dll needs the MSVC runtime (MSVCP140, VCRUNTIME140) and `libwinpthread-1.dll`. Inside AstroBot.exe it binds to AnyPS5's MinGW winpthread (tested: loads and binds), but Kyty's threads have not run on it yet.
6. No CMake target yet: the DLL is built by the script from the existing emulator objects. A `kyty_gpu` target in Kyty's CMakeLists is left out until it can be configured and tested in its own build directory.
